# `report/` — per-regime fusion tables

Five CSVs, one per benchmark regime, generated by `python -m glm52.make_report`:

| file | tokens | o_proj K | MoE rows (T×8) |
|---|---|---|---|
| `fusion_decode_bs1.csv` | 1 | 32768 (absorbed MLA) | 8 |
| `fusion_decode_bs32.csv` | 32 | 32768 | 256 |
| `fusion_decode_bs256.csv` | 256 | 32768 | 2048 |
| `fusion_prefill_t2048.csv` | 2048 | 16384 (non-absorbed) | 16384 |
| `fusion_prefill_t8192.csv` | 8192 | 16384 | 65536 |

Each file has the same 15 rows — every **measured** fusion variant. The two candidates
filtered on analysis (#2 o_proj+ResAdd+RMSNorm, #7 Up_Gate+Act+Down) are **not** included;
see `log/LOG-00-plan-and-filter.md` §3 for why they were rejected without implementation.

All times are **milliseconds, p50**, bf16, MetaX C500, one exclusive GPU.

## Columns

| column | meaning |
|---|---|
| `fusion` | the fusion strategy, numbered as in the original candidate list |
| `variant` | which implementation of that strategy (some have two: e.g. atomic vs token-major) |
| `replicates` | the production reference the Triton kernel was **actually** modelled on. `none (custom)` where the kernel has no upstream analogue. |
| `coda_correspondence` | whether the fusion matches CODA's GEMM-plus-epilogue abstraction (Guo et al. 2026). **Conceptual mapping only** — no kernel here was written from CODA; see below. |
| `fused_ms` | the fused variant, timed as one chain with a single L2 flush before it |
| `fused_mapping` | the mapping the fused kernel ran at |
| `unfused_total_ms` | the whole unfused chain, timed the same way — **this is the authoritative unfused number** |
| `speedup` | `unfused_total_ms / fused_ms`; >1 means the fusion helps |
| `n_unfused_kernels` | how many kernels the unfused chain launches |
| `unfused_kN_name/_ms/_mapping` | kernel N of the unfused chain: what it is, its time **measured alone**, and the mapping it ran at |
| `notes` | caveats specific to that row |

Mapping abbreviations: `BM`/`BN`/`BK`/`BE` = BLOCK_M/N/K/E, `BD` = BLOCK_DIM,
`BLK` = BLOCK, `GM` = GROUP_M, `SK` = SPLIT_K, `w` = num_warps, `s` = num_stages,
`NBK` = NORM_BK, plus kernel-specific flags (`KVEC`, `UNROLL`, `EVICT`, `impl`).

## Reading the per-kernel times correctly

`unfused_kN_ms` is that kernel **timed alone**. The parts routinely sum to **more** than
`unfused_total_ms`, and that is expected, not an error:

- timed alone, each kernel pays its own launch overhead and its own L2 flush;
- inside the chain, the second kernel's input is still L2-hot and launches partly overlap.

For sub-0.1 ms kernels this makes the parts sum to 1.1–1.4× the total. **Use
`unfused_total_ms` for any speedup arithmetic**; the per-kernel columns are for seeing
where the time goes, not for re-deriving the total.

The generator does flag the one thing that is genuinely impossible — a *single* kernel
slower than the whole chain containing it. That check currently passes on every row.

## Data provenance and corrections

Two numbers in these tables were not taken verbatim from the original benchmark JSON:

1. **#1 o_proj+ResAdd, all regimes** — the original run recorded only the chain total, never
   the per-kernel split (flagged as a recording gap in `log/LOG-08` §F12). The main session
   re-measured both kernels at the recorded unfused mapping; results in
   `results/_f01_perkernel_split.json`. At `prefill_t2048` the first pass returned a GEMM
   time larger than the whole chain; re-measuring over 5 passes gave a stable
   4.183 ms (chain 4.236 ms), and the stable value is what appears here.
2. **#6 Up_Gate+SwiGLU, prefill_t8192** — the sequential timing block recorded
   `unfused_gemm_ms = 52.2173 ms` against a chain total of 38.6678 ms, which is impossible.
   The F6 agent caught this itself and re-measured with an interleaved A/B protocol; the
   median of those 4 rounds (**37.8902 ms**, spread 37.87–37.93) is used here, and the row's
   `notes` says so. The independent audit reached the same conclusion (`log/LOG-08` §F8).

Everything else is verbatim from `results/*.json`.

## On the CODA column

**CODA** — Guo et al., *"CODA: Rewriting Transformer Blocks as GEMM-Epilogue Programs"*
(MIT / Princeton / Together AI / Meta, arXiv 2605.19269, May 2026) — is a **paper and kernel
abstraction**, not a library any kernel here was ported from. None of the implementations in
this study were written from CODA, and its code was not consulted.

The `coda_correspondence` column therefore records **conceptual correspondence only**: whether
the fusion is expressible as CODA's "GEMM mainloop fixed, composable epilogue" pattern.
`yes` for the GEMM-epilogue fusions (#1, #6, #8/#9, #11b′), `partial` for the prologue-shaped
Lazy Pre-Norm (#11a/#11b — CODA is epilogue-oriented), and `no` for fusions with no GEMM (#3,
#10) or that fuse in the opposite direction (#4/#5 push the GEMM *into* a normalization
kernel).

That distinction turned out to matter empirically: every `yes`/`no-GEMM` row that wins does so
as an epilogue or a pure vector fusion, while the `no — inverse direction` rows (#4/#5) are the
worst results in the study at 0.21–0.68×. See `log/LOG-09` §3.

## Reference priority actually used

Per the task's stated priority (cuBLAS > CUTLASS > sglang > torch > other engines):

- **cuBLAS-equivalent**: MetaX's vendor BLAS via `torch.matmul` / `torch.addmm` — the
  absolute reference line for every GEMM-shaped kernel.
- **CUTLASS**: not available for MACA; no kernel replicates it.
- **sglang 0.5.10**: structural reference for the MoE path (`fused_moe_kernel`,
  `moe_align_block_size`, `MUL_ROUTED_WEIGHT`, `FUSE_SUM_ALL_REDUCE`, `fused_add_rmsnorm`,
  `moe_sum`, `biased_grouped_topk`). Source consulted, not installed.
- **torch**: `reference.py` fp32 implementations, used as correctness ground truth.
- **PyTorch/Meta "Towards Free Normalization"** (Zhou et al., 2026-07-10): the algorithm for
  #11.

`glm52/kernels/REFERENCES.md` maps each kernel to its reference in more detail.

## `layer_optimal_per_regime.csv`

Whole-layer (S3-S11 + shared expert) end-to-end measurement of fusion **combinations**, not
individual fusions. 36 rows: every configuration measured, per regime, with both interleaved
A/B runs. Columns: `regime, fusion_set, config_id, run1_ms, run2_ms, best_ms,
speedup_vs_unfused, tied_with_best_run1, tied_with_best_run2`.

`tied_with_best_*` = 1 means that configuration was **statistically indistinguishable** from
the best one in that run (gap below the round-to-round spread). Treat a row with
`speedup_vs_unfused` near 1.00 and `tied=1` as "no measurable difference from doing nothing".

Optimal combination per regime (full reasoning in `log/LOG-11-optimal-per-regime.md`):

| regime | optimal | vs all-unfused |
|---|---|---|
| decode_bs1 | #3 + #10 | 1.0046x (borderline) |
| decode_bs32 | #3 + #8 | 1.0037x |
| decode_bs256 | #8 (or #3 + #8) | 1.0037x |
| decode_bs512 | #3 + #10 | 1.0015x |
| decode_bs1024 | #3 + #10 | 1.0024x |
| prefill_t2048 | #3 + #10 | 1.0024x |
| prefill_t8192 | #3 + #10 | 1.0039x |

One rule: always enable #3; on the down axis use **#8 only for T <= 256** and **#10 from
T = 512 upward**; never #6, never #1 at prefill, never fuse greedily (greedy costs up to +48%).

Regenerate with `python -m glm52.make_layer_report`. All 7 regimes are measured twice
independently; `tied_with_best_run1/2` carry each run's own verdict, so disagreement between
the runs is visible rather than averaged away.

## `f8_gain_vs_batch.csv` / `.png` / `_dark.png`

Fusion **#8** (MoE down-projection GEMM + expert merge) kernel-level gain across 20 decode
batch sizes, 1 -> 1024. `gain = unfused / fused`, so >1 means the fusion helps.

    UNFUSED : w2 grouped down GEMM -> [rows, H] , then moe_sum over top-8 -> [T, H]
    FUSED   : the same GEMM with sglang's FUSE_SUM_ALL_REDUCE atomic-accumulate epilogue,
              plus the output zero-init it requires (inside the fused timing)

**Both sides are independently retuned at every batch point** — the optimal BLOCK_M shifts
with rows-per-expert (T*8/256), so a fixed mapping would render mapping staleness as apparent
batch-size structure. Each point is the median of 5 interleaved rounds; `gain_spread_pct` is
the round-to-round range (0.02-0.4% throughout, so the curve's shape is resolved, not noise).
Both sides validated against an fp32 reference at every point.

The `source` column matters: most points come from the lane sweep, which varies (BM,BN,BK)
with warps/stages held at the seed. At **T=768/896/1024** that missed the fused optimum, so
those three were re-tuned on a **wide grid (486 configs per side, full tile x warps x stages
x group cross, both sides equally)** and those values supersede the swept ones. The
correction was large at the tail — T=1024 went 0.786x -> **0.903x** — and T=768 was re-tuned
as a control, agreeing to 0.2%.

Headline: **#8 is never *clearly* worth anything, and is clearly harmful from T = 896.**
Its best measured point (1.012x at T=64) is inside the between-run uncertainty, so no
positive gain is established at any batch size. By T=1024 the fusion costs **10%**, which is
well outside the noise. Worth enabling only for small decode batches, consistent
with sglang gating `FUSE_SUM_ALL_REDUCE` behind a flag.

> **READ THE ERROR BARS CORRECTLY — they understate the uncertainty.** `gain_spread_pct` is
> the range over 5 interleaved rounds *within one process at one tuned config* (0.02-0.4%).
> It does NOT include tuning variance or process-to-process variance. Comparing the same
> quantity against the independent earlier measurements in `fusion_decode_bs*.csv` gives
> diffs of -2.46% (T=1), -1.14% (T=32), -0.61% (T=256), +0.80% (T=512), +6.05% (T=1024) --
> a mean absolute difference of **2.21%, about 20x the plotted spread**.
>
> Consequences: the plateau's shape between T=8 and T=512 (range 0.979-1.012) is **within
> the between-run uncertainty and is not resolved** -- individual wiggles such as T=32
> dipping below 1.0 should not be read as real. The break-even *location* is likewise only
> pinned to T ~ 256-512, not to a specific pair of points. What IS outside the noise: the
> tail at T=896 (0.942) and T=1024 (0.903), and the overall conclusion that the fusion never
> buys more than ~1%.
>
> Getting honest error bars needs N independent repeats per point in fresh processes with
> fresh tuning, which has not been run.

> **Supersedes:** the `#8` row of `fusion_decode_bs1024.csv` reports 0.851x. That fused side
> was also under-tuned; the wide re-tune's **0.903x** is the better-tuned value. The
> `fusion_decode_bs*.csv` tables were not regenerated.

Regenerate with `python -m glm52.plot_f8_sweep` (reads `results/f8_sweep_*.json`).
Palette is the validated categorical slots 1-2; light and dark figures use their own steps.

## `f9_gain_vs_batch.*` and `f8_f9_gain_vs_batch.*`

Fusion **#9** (down-GEMM + expert merge + **ResAdd2**) across the same 20 decode batch sizes,
same protocol as #8: both sides independently retuned at every point, median of 5 interleaved
rounds, all three variants validated against an fp32 reference.

#9's unfused side has two legitimate forms and **both are reported**, because the choice is
what LOG-08 F4 caught inflating a result:

| baseline | chain |
|---|---|
| **2-kernel** (honest) | down GEMM -> `moe_sum(ADD_RESIDUAL=True)` |
| **3-kernel** | down GEMM -> `moe_sum` -> separate `resadd` (materialises a [T,H] tensor nothing needs) |

The fused side's residual seed is inside its timing, taken as the better of a torch `.copy_()`
and a tuned Triton seed kernel — the fused side gets its own best option.

**Results.** Same shape as #8: **no resolvable gain at any batch size**, and a clear
regression at the top — 0.939x (T=896) and **0.911x (T=1024)** against the 2-kernel baseline.
Best nominal point is 1.011x at T=64, inside the ±2.2% between-run uncertainty, so no positive
gain is established anywhere. The 3-kernel baseline flatters the fusion by only 0.2-0.5% at
most sizes — but at **T=1 it is worth 2% and flips the sign** (0.997x vs 1.017x), which is
exactly the regime where the audit found it mattering.

**`f8_f9_gain_vs_batch.png`** overlays the two fusions. They are indistinguishable across the
whole sweep, i.e. **folding ResAdd2 into the fused down-GEMM costs nothing measurable** — if
you are already paying for #8's atomic merge, #9 is free; and since #8 has no demonstrable
upside, neither does #9.

Cross-check worth noting: #9's independently tuned fused kernel lands within **±0.5%** of #8's
*wide-re-tuned* values at every batch size, including T=896/1024 where #8's original lane
sweep was wrong (#9 found 6.024 ms at T=1024 vs the wide re-tune's 6.071 and the bad lane
sweep's 6.968). Two independent tunings of the same kernel agreeing confirms the corrected
#8 tail — so no wide re-tune was needed for #9.

Regenerate with `python -m glm52.plot_f9_sweep`.

## `f8_f9_gain_vs_prefill.{csv,png,_dark.png}`

Fusions **#8** and **#9** across the prefill range, **T = 256 .. 262144** (11 log-spaced
points), same protocol as the decode sweeps: both sides independently retuned at every point,
median of interleaved rounds, fp32-validated.

**T = 262144 is the hard ceiling on this GPU.** The problem allocates ~167 KB per token
(activations, the `[8T, 6144]` unfused intermediate, and three `[T, 6144]` buffers) on top of
the fixed 6.4 GB `w2`, reaching **47 GiB of 64** — measured, not estimated. **T = 1M would
need ~175 GB, 2.7x the card**, so it cannot be run here.

Note these two kernels have **no distinct prefill mode**: they touch only the
down-projection, whose shapes depend on `rows = T*8` and nothing else (unlike o_proj, whose K
changes between the absorbed and non-absorbed MLA paths). This is the decode curve continued
to larger T, presented separately only because the study's vocabulary splits the two.

**Result: no prefill size where either fusion pays.** Break-even is at T ~ 256-512; from
T = 1024 upward both lose **9-15 %**, ending at **0.853x (#8)** and **0.852x (#9)** at
T = 262144. Those margins are 4-7x the between-run uncertainty, so unlike the decode plateau
this is firmly resolved. The 2-kernel vs 3-kernel baseline distinction, which was worth 2 %
at T=1, is ~1 % here — below the resolution floor and not claimable.

Measurement effort scales with size (`rep_budget()` in the sweep scripts): 4/12 tuning +
8/25 measurement up to T=8192 — identical to the decode sweeps, so those points stay directly
comparable — then 2/6 + 4/10, then 1/3 + 2/5 above T=65536. At T=262144 one chain launch is
1.73 s, so a fixed rep count would have cost ~80 min per point for no gain in precision.

**Six points were re-measured on the wide grid** (486 configs/side, full tile x warps x
stages x group cross, both sides equally); the `*_source` columns record which. The lane
sweep's tile search holds (warps, stages) at the seed and under-tuned them:

| point | lane sweep | wide re-tune |
|---|---|---|
| #8 T=1024 | 0.7794 | **0.9024** |
| #8 T=2048 | 0.9663 | **0.9038** |
| #8 T=4096 | 0.9470 | **0.8867** |
| #9 T=1024 | 0.8516 | **0.8990** |
| #9 T=2048 | 0.9602 | **0.8986** |
| #9 T=4096 | **1.2981** | **0.8872** |

The #9 T=4096 case is the cautionary one: the lane sweep reported a **30 % speedup** that was
purely an under-tuned baseline.

**Cross-campaign consistency (this is the useful part).** T=256/512/1024 were measured
independently in both the decode and prefill campaigns. After the re-tune:

- T=256: **0.02 %** apart (#8), 0.01 % (#9)
- T=512: **0.16 %** apart (#8), 0.23 % (#9)
- T=1024: decode 0.9025 vs prefill **0.9024** (#8) — agreement to 4 decimal places

So the machine's true run-to-run reproducibility is **~0.2 %, not 2.2 %**. The 2.2 % figure
quoted on the decode figures conflates timing jitter with *tuning-quality* differences, and
tuning quality is the dominant error source throughout this study. The ±2.2 % envelope on the
charts is therefore conservative; treat it as an upper bound on uncertainty, not an estimate
of jitter.

Regenerate with `python -m glm52.plot_prefill`.
